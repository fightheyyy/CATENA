# 为什么编程 Agent 的 Trace 很难“照着日志画出来”

一条编程 Agent 会话并不是一条整齐的请求—响应。模型消息、工具调用、工具结果、恢复上下文和子 Agent 活动会交错写进本地记录。若简单按时间戳把行拼成对话，容易把启动时恢复的旧消息当成新 Turn，把工具输出挂到错误的调用上，或把尚未结束的任务标成成功。

我在 Catena 中把解析分成两步。第一步保留运行时的原生身份：Codex 的 session/turn/call ID、Claude Code 的消息 UUID 和 tool-use ID。第二步才生成统一的 Event Graph：每个 Turn 有模型步骤、工具节点、来源事件 ID、状态和时间范围。工具结果按 call ID 匹配，不能只靠相邻行；缺失结果明确标 `incomplete`，取消和中断也单独记录。

这一步还有一个容易漏的细节：工具调用的外层状态可能是 `ok`，但里面的 shell 进程退出码非零。它只证明那次命令失败，不证明整个用户任务失败。Catena 的离线研究因此只把非零退出、重复失败调用和重复相同调用列为**待核对线索**。正常轮询、故意运行失败测试、随后已恢复的调用都可能推翻最初的猜测。

可追溯性比漂亮的图更重要。Catena 通过原生 ID 生成稳定 Trace/Span ID，重复导入可按同一身份替换；每个规范化节点保留来源事件 ID。分析时固定一组 Trace 和内容摘要，生成的候选文件能回到原始 Turn。上游日志是证据，不是给分析 Agent 的指令。

我用自己的历史记录做了第一轮离线试跑：282 个可解析会话、1,828 个 Turn，16 个 Turn 带有至少一个待核对信号；15 个过大的源文件按当前上限跳过。初版曾把 `exec` 封装的后台等待误认为重复执行，修正后待核对 Turn 从 36 降为 16。这些是**覆盖和审查量**，不是误报率，也不是已证明的失败数。下一步按固定随机种子同时抽取有信号和无信号的 Turn，人工判定是否值得修，再把确认的问题变成回归案例。只有在相同案例、相同时间上限下比较 Skill 前后结果，才能说改进有效。

这项工作的难点不是把日志塞进一个大模型，而是守住几个边界：原生身份不混淆、工具效果不靠猜、未知不当成功、候选不当验证。Trace 还原正确，后面的分析才有资格被相信。
