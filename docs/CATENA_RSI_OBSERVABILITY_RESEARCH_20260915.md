# Catena：RSI、观测平台与自我剖析的竞争判断

核查日期：2026-09-15，北京时间。

**当前建议：继续做 Catena，将下一版聚焦为好看、精简的跨 Agent 云端工作台，连通 Trace 浏览、长期记忆、自我剖析和可复用产出。** 优先验证这条完整使用流程；通用工程观测基础设施和全自动 RSI 的扩建仍应控制范围。跨会话分析、候选改进、评测比较和历史记录已有竞争，需要以接入体验、查找效率、记忆质量和实际产出来检验产品价值。

用户进一步明确的目标：Claude Code、Codex、Hermes、OpenClaw 和其他 Agent 继续在端侧运行，通过其 OTLP 导出能力或适配器向云端汇集记录。用户在一个网站里观测经历、积累记忆、剖析自己或团队，并从经历中生成有用的东西。好看、精简、云端、多 Agent 是产品要求；自我剖析是持续使用体验的一部分，前一轮将产品收窄为画像报告并不完整。

建议按三类材料组织体验：保留可回看的原始经历；从有依据的记录提炼可修正的个人或项目记忆；按用户需要生成复盘、知识笔记、工作流程或 Agent 配置候选。记忆应区分用户陈述、模型建议、工具结果和分析推断，并保留来源及时间。此处记录的是产品方向，尚未改变现有 SPEC 中的实现范围。

OTLP 负责遥测数据的编码、传输和交付，并不保证每个导出器都提供完整对话与任务内容。因此统一接入之后，还需识别会话关联和内容覆盖：只有时延、费用等数据时提供基础观测；材料足够时才生成相应记忆与剖析。网站应直接说明已收到什么、可以做什么。本次未逐一验证上述 Agent 的原生 OTLP 能力，也未将它们都记作已完成集成。[OTLP 官方规范](https://opentelemetry.io/docs/specs/otlp/)

本报告补充[个人与团队自我剖析调研](./CATENA_SELF_REFLECTION_RESEARCH_20260915.md)。上一份覆盖的是新产品方向，本次加入 Catena 原有技术路线的竞争：8 个自我改进相关项目、1 个 RSI 评测项目和 7 个观测平台。RSI 在这里按 Recursive Self-Improvement 理解，同时专门检查了具体项目 Skill-RSI。

依据是项目官方文档、公开仓库与作者实验记录，并对照本地 README、SPEC。下文“支持”“提供”表示公开材料记载的能力，不能理解为本次全部安装验证过。未运行付费模型实验，未上传私人历史，未复现论文结果，也没有把 GitHub stars 当成活跃用户或商业成功。比较是代表性抽样，不能证明市场不存在其他实现。

**RSI 相关项目需要按改进对象区分。**

提示词、Skill 或 Agent 代码的候选搜索，模型权重的强化学习，以及科研任务的自动实验，对资源和评测的要求不同。它们都与自我改进有关，但不能把一个有评分器的循环直接等同于通用递归智能，更不能据此声称可以准确理解人的人格。

| 项目 | 输入、改进对象与公开流程 | 关键边界 | 与 Catena 的关系 |
| --- | --- | --- | --- |
| [Kayba recursive-improve](https://github.com/kayba-ai/recursive-improve) | 从捕获或已有 Trace 发现跨运行问题；区分代码与提示词修复；生成修改，比较版本；另有 ratchet 循环和仪表盘 | 动态生成的诊断指标有利于发现问题，但不能代替固定评测材料上的独立验证 | 对 Catena 原有“证据→跨 Run 分析→改进候选”流程构成直接竞争 |
| [Skill-RSI](https://github.com/justinwetch/Skill-RSI) | 从目标或已有 Skill 开始，生成挑战版本，与当前最佳版本比较，保留实验和后续计划；提供本地 UI、CLI、Codex 插件 | 评测对象是 Skill 产物；不是导入个人使用史后生成个人档案。公开流程存在不等于效果已获外部验证 | “进化过程可看、结果可比较、失败可积累”已有独立产品实现 |
| [EvoSkill](https://github.com/sentient-agi/EvoSkill) | 从 benchmark 失败轨迹提出新 Skill 与提示词，用评测选择候选，通过 Git 保存版本与历史；支持多个编码 Agent | README 将“无 benchmark 进化”列为研究方向，“日常使用中持续改进”列为开发中 | 对 Catena 的 Skill 候选生成与版本管理重叠高；不能把其路线图计作成熟能力 |
| [GEPA / gskill](https://gepa-ai.github.io/gepa/guides/gskill/) | 从仓库任务与失败反馈学习适用于该仓库的技能；示例包含训练、验证和最终留出测试 | gskill 的示例依赖任务、测试与运行环境。GEPA 是可复用优化工具，不是完整个人或团队分析产品 | 若以后需要验证具体 Agent 改动，值得评估复用；无须重新实现一种通用优化器 |
| [Hermes Agent Self-Evolution](https://github.com/NousResearch/hermes-agent-self-evolution) | 基于 DSPy、GEPA 进行候选搜索、评测、约束检查和 PR 交付 | 状态表只将 Skill 进化标为已实现；工具描述、系统提示词、工具代码和连续流水线仍在计划中 | 技术方向很接近，但成熟范围比标题窄；适合观察其评测与交付方式 |
| [Microsoft Agent Lightning](https://github.com/microsoft/agent-lightning) | 当前 v1.0 围绕 Trainer、API Gateway、Rollout Controller，让真实 Agent 运行参与强化学习 | 涉及策略模型训练和 GPU 环境；与只调用外部模型 API 改写 Skill 的成本结构不同 | 作为模型训练路线参照，当前不适合成为 Catena 自我剖析首版的核心依赖 |
| [Karpathy autoresearch](https://github.com/karpathy/autoresearch) | 原项目让 Agent 修改训练代码，以固定时长实验和固定验证指标保留或丢弃修改 | 原项目针对单 GPU 模型训练，数据准备与评价框架固定；不是通用 Agent 历史分析平台 | 最值得借鉴的是范围清楚、每轮有假设、结果容易核对的体验 |
| [Sakana Darwin Gödel Machine](https://sakana.ai/dgm/) | 修改编码 Agent 自身代码，运行编程评测，保留候选档案并探索不同分支 | 属于研究系统；作者在特定任务中的结果不能外推到任意 Agent 或人的成长 | 说明“会改自己”也有严肃研究竞争；Catena 无须以复现这条研究路线证明产品价值 |

Skill-RSI 的详细文档还有两个值得注意的设计：它使用稳定测试与探索测试，并且晋升条件包含回归约束，分数略高不一定替换旧版本；历史同时保存详细产物和供下一轮使用的简要记忆。其评测集也会演变，因此长期总分趋势仍需结合测试组成解释，不能直接当成统一尺度上的持续提高。[工作原理](https://github.com/justinwetch/Skill-RSI/blob/main/docs/HOW_IT_WORKS.md)

另查了 [RSI-Exam](https://github.com/aiming-lab/RSI-Exam)：这是评测基础设施，2026 年 8 月公开的数据包含 35 项任务，另外 53 项保留。它让 Agent 在可见材料上实验，再将提交产物放入独立环境，在未见数据上重新评分。对 Catena 的启发是把“提出了改进”“在开发样本上得分更高”“在新任务上更有效”分成不同证据状态；它本身不是用户画像产品。

以上项目使用不同模型、任务、预算和评分方式，本报告不横向排列作者公布的提升百分比。没有统一条件，数字更大不能证明方法更强。

**观测平台已经开始替用户解释问题和组织改进。**

| 平台 | 本次核实的能力 | 可用性或能力边界 | 对 Catena 的含义 |
| --- | --- | --- | --- |

最接近 Catena 现有接入方向的是 Braintrust 的官方编码 Agent 实践：团队汇总 Claude Code、Codex、OpenCode、Pi 的实时记录，其中 Codex 和 Claude Code 支持导入保存的历史；定期分析重复问题并形成 Patterns。跨工具、历史导入、团队聚合和周期分析已有组合示例，不能再单列为独有亮点。[2026-08-19 官方实践](https://www.braintrust.dev/docs/cookbook/recipes/CodingAgentInsights)

这些流程的主要目标仍是 Agent 工作质量与系统问题，不足以证明已经做好了人的长期自我理解。它们也不证明整个产品容易使用：本次没有做统一任务的接入计时或可用性测试。Catena 仍可能在特定人群的理解成本上做得更好，但需要实际比较。

Langfuse 的编码 Agent 页面同样覆盖团队使用、Trace、技能与评测；其中自有 Gateway 在核查时标为 coming soon，不能当作已上线。其团队还公开了一个将 autoresearch 应用于 Skill 的实验。[编码 Agent 场景](https://langfuse.com/coding-agents)

**“评测更高”与“更符合真实需要”之间存在产品风险。**

Langfuse 的这次实验产生了一些有效改动，也删掉了测试没有覆盖的能力，并为了适应无人交互环境移除了原有人工确认步骤。作者最终只选取部分修改，没有接受全部高分版本。这支持一个具体判断：评价目标和实验环境不完整时，自动优化可能减少真实使用价值。[作者实验记录](https://langfuse.com/blog/2026-03-24-optimizing-ai-skill-with-autoresearch)

Opik 官方 FAQ 也明确区分优化材料与验证材料；未提供独立 validation_dataset 时，训练与候选排名使用同一数据，容易过拟合。[优化 FAQ](https://www.comet.com/docs/opik/development/optimization-runs/faq)

这关系到 Catena 的两个层面。对于 Agent 改进，应检查新任务效果、原有能力回归和运行成本；对于个人剖析，应检查引文是否支持结论、是否存在相反经历，以及用户补充情境后结论是否需要修正。不能用生成报告的模型再给报告一个高分，就把它当成可靠理解人的证据。

**与 Catena 现状对照后，主要问题是产品价值尚未被证明。**

本地 [README](../README.md) 与 [SPEC](../SPEC.md) 描述的主线是：采集运行证据，跨 Run 分析，由 Inspector、Evolution、Reviewer 产生 agent.md、Skill、Role 等候选。Catena 不执行用户的目标 Agent，实际 Explore、Replay、Compare 与发布验证归本地 Barena。这个边界清楚，值得保留；不能把候选已经生成说成目标 Agent 已经变好。

| Catena 现有资产或目标 | 此次调研后的判断 | 下一步应证明什么 |
| --- | --- | --- |
| Codex、Claude Code 记录解析与统一事件 | 有复用价值，但其他项目也能导入或采集这些来源 | 所选用户能顺利带入足够材料，且材料保留了分析需要的情境 |
| 按 Turn 阅读 Trace 和查证原始记录 | 是可信分析的基础，单独作为产品亮点偏弱 | 用户从发现到核对依据是否足够省力 |
| Trace Farm 跨运行分析与改进候选 | 与 recursive-improve、EvoSkill、Braintrust 等重叠明显 | 在同样材料和预算下，比现成流程多带来什么有用结果 |
| 候选交给端侧验证 | 边界合理；需要真实任务验收才能说明改进效果 | 固定基准、独立新任务、回归和成本是否都可追溯 |
| 从使用 Agent 理解个人 | 本轮观察到的工程优化工具不能直接覆盖全部目标；上一轮已找到直接自我剖析竞争 | Catena 的具体发现是否优于现成报告或通用提示词，且用户愿意再看 |
| 从多人的 Agent 理解团队 | 仅汇总 Agent 不能还原团队；还需要成员、角色、共同任务和情境 | 成员是否认可分析依据，是否真的帮助共同复盘，并愿意继续使用 |

配置、记忆和行为提供不同材料。配置可能表达期望，也可能直接来自公共模板；记忆可能是模型整理的摘要；工具错误可能来自权限或环境。同一人使用多个 Agent、多人共用一个 Agent 都可能发生。因此 Agent ID 不能自动当成人的身份，Agent 失败也不能直接归因于人的缺点。这是分析质量的实际约束。

**值得验证的体验，应当让用户获得对自己更具体的理解。**

一个可测试的产品表达是：导入你和 Agent 的工作记录，看到自己在不同任务里的决策、协作习惯及变化，每个发现都能查看依据、补充背景、修改或否定。跨工具和本地处理可以降低使用障碍，但是否构成优势，仍取决于报告质量和持续使用。

例如，若记录提供足够依据，报告可以指出：“在探索方案时，你倾向于保留多个选项；进入交付阶段后，你仍经常重开已经决定的问题。这个现象集中在需求尚未写清的任务，在维护任务中并不明显。”这是体验示例，不是对项目主人或任何真实成员的分析。它比一个笼统标签更便于核对，也给用户补充任务背景的空间。

持续价值来自旧观察被新材料补充、限制或推翻，而不仅是每周重新生成一份相似的文字。团队版还应围绕共同任务，帮助成员理解不同的完成标准、分工与交接习惯；个体之间的简单分数排名无法回答这些问题。

RSI 可以服务其中一个后续动作：用户认可某个观察，也愿意尝试改变时，再提出具体的工作约定或 Agent 配置实验，并在后续任务中比较。用户也可能只想理解自己的偏好和优势，不希望调整 Agent；自我剖析本身就需要成立。没有必要让所有报告最终都变成生成 Skill。

“更能解释自己”仍是产品假设。上一轮已经核实 Claude 原生反思、KnowMe、mentor 等直接或邻近竞争，不能因为工程观测平台偏重系统，就将个人理解宣布为无人区。原生工具的导入成本较低，也会给独立产品带来竞争压力。[原有自我剖析调研与来源](./CATENA_SELF_REFLECTION_RESEARCH_20260915.md)

**是否继续投入，建议按以下选择执行判断。**

| 方向 | 当前建议 | 理由 |
| --- | --- | --- |
| 完整通用观测平台 | 暂停扩大范围 | 基础能力成熟，助手也在降低理解门槛；缺少支持 Catena 正面竞争的证据 |
| 通用 Trace→Skill 自动进化平台 | 不作为唯一卖点继续重投入 | 已有直接竞争，评测任务和真实收益验证的成本不低 |
| 围绕个人工作方式的自我剖析 | 保留一次短验证 | 最接近用户的产品意图，现有采集和证据资产可复用；差异与留存仍未知 |
| 团队自我剖析平台 | 等个人体验和真实团队需求成立再扩展 | 身份、共同任务和成员参与增加了产品工作量，不能靠多 Agent 汇总替代 |

延续前一份报告的两到三周验证建议，但比较基准需要补充：

1. 个人剖析与普通提示词、mentor／原生报告比较，尽量使用相同材料，并单独检查跨工具数据带来的增量。
2. 若保留工程改进演示，选一项范围窄、能重复运行的真实任务，比较 Catena 与一个可用的现成改进流程；在运行前固定评价方式与预算，并保留未用于优化的新任务。
3. 两项成绩分开记录。Agent 测试提高，不能代替用户觉得报告有用；用户觉得文字贴切，也不能代替实际执行效果。
4. 继续投入的核心信号仍是：用户能指出有依据的新理解，并自主带新记录回来。若报告与通用提示词差异很小，或只有首次好奇，就收缩为轻量开源工具，不继续扩建平台。

综合用户澄清后的立场：**支持继续做聚焦的 Catena 云端工作台，保留观测、记忆、剖析与产出这条主线。** 验证应覆盖整条流程的持续使用价值，不能只凭画像报告的竞争情况否定项目。现有代码可以复用，后续投入则应依据用户是否能方便地找回经历、获得可靠记忆、产生有用成果以及持续使用。若完整体验仍无法显示相对价值，再考虑收缩或转向其他项目。

本次只补充研究文档，不改变现有架构合同，也不启动部署或自动优化运行。
