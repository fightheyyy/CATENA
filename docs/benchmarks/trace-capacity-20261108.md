# Collector Trace 容量阶梯（2026-11-08）

结论：本机未达到持续 3000 Span/s。高压档通过增加拒绝/未发送量保持有界，不能把输入目标写成落库容量。1000 Span/s 全确认且无观察查询超时；1500 Span/s 全确认但出现积压与尾延迟。

## 配置与口径

- 4 CPU 配额 / 32 GiB，同机 Go 1.25.11、真实 PostgreSQL 鉴权、2 Go HTTP Ingress（同一测试进程）、2 Collector Gateway、2 Consumer、3 Kafka Broker（RF=3/minISR=2）、12 分区、ClickHouse 25.10.2.65。Collector 0.137.0 / Kafka 3.9.1。
- 沿用 A/B 的约 3377.86 字节/Span，1KiB 输入 + 2KiB 输出重复字符，100 Span/请求，20 租户。每档独立数据库，先用 100 个批次串行预热，随后目标负载持续 60 秒。
- Go 入口每进程并发 16 / 每 Owner 2；生成器最大 128 在途请求，压力请求不自动重试。达到生成器上限的 offer 单列为未发送，不冒充服务端接收或丢失。请求生成/Ingress 和观察查询也占用同机资源。
- 每 200ms 加查询时间观察可见性，查询超时为 2 秒。高压时观察出现超时，因此可查询 P95 是带观察误差的上界，不适合用作精确服务 SLO。
- 独立复核 system.query_log 的 QueryFinish INSERT 完成时刻和 written_rows。每档完成日志总行数与最终唯一 Span + 10000 个预热 Span 一致，没有重复行，因此 60 秒内的 INSERT 完成行数可作为本次唯一落库窗口吞吐。不是 Kafka ACK 吞吐，也不是停止发送后的排空吞吐。

端到端观测取确认和可查询时间的较晚者，分位数只针对成功请求，拒绝率另表列出。高压查询超时造成遗漏观察时段，不能直接把该 P95 当作纯写入延迟；INSERT 完成日志只复核吞吐，不伪造逐请求提交延迟。

## 可使用的工程表述

在 4 核 / 32 GiB 单机、约 3.38KB/Span 的合成负载下，完成 60 秒、目标 1000 Span/s 基线（窗口实际 INSERT 完成约 995 Span/s，60000 Span 全部确认并最终落库；可查询观测 P95 约 2090ms）；另完成 3000–20000 Span/s 压力探索，验证入口背压与有界并发，未达到持续 3000 Span/s。
独立停库验收已证明：ClickHouse 停机 10 秒期间，Kafka 可承接并确认当时到达的 10000 Span，恢复后全部落库。这是独立故障实验，不与本轮容量阶梯伪装成同一轮；见 [A/B 报告](trace-writer-collector-ab-20261108.md)。
不建议把本轮峰值约 2000 Span/s 写成无拒绝、低延迟的持续容量，更不能写“持续 10000/20000 Span/s”。若要提高可靠的容量声明，需要在独立压测端、长稳态、多轮复验及明确延迟/拒绝率门槛下重新验证。
