# 旧 Writer / Collector 同机 A/B（2026-11-08）

旧版来自 Git 提交 `7e6c8b386f780fa2c03c4792f953b9c82704123d` 的完整 backend 归档，不是对新版调大并发来模拟旧版。当前工作区未重置；新架构代码保持不变。

## 实验方法

- Linux 同机，CPU 配额 4 核、内存上限 32 GiB，Go 1.25.11 / GOMAXPROCS=4，ClickHouse 25.10.2.65，真实 PostgreSQL 鉴权。
- A：原始 Go API → 自研 Writer → ClickHouse；B：当前 Go API → Collector Contrib 0.137.0 → Kafka 3.9.1（三 Broker、12 分区、RF=3/minISR=2）→ 1 Consumer → 官方 Exporter。每边都是 1 个 Go Ingress；B 使用 1 Gateway。
- A 运行时停止 Kafka/Collector；B 运行时启动它们，计入整机资源成本。逐轮新建 ClickHouse 数据库，预热 10 秒后测量 60 秒，顺序 A→B→B→A，两边各两次。
- 两边共用同一份测试生成器，20 租户、每进程入口并发 16 / 每 Owner 2，目标 10 请求/s × 100 Span/请求。每 Span 含 1KiB 输入 + 2KiB 输出（重复字符合成数据）。
- OTLP 公共输入每 Span 平均 3377.9 字节（含均摊信封），每轮 60000 Span；四轮请求体 SHA-256 完全一致：`9ebf8010bbc6afd299f597b7a4e2d38f44f3fc5e169377df19d0f9e2d9b54b3c`。鉴权头/Owner 及内部存储元数据不属于这个请求体哈希。
- 不是极限吞吐测量。有效吞吐为全部唯一 Span 完成 / 首次入队到最后一次“确认且可查询”的时间；端到端耗时取 HTTP 确认和 ClickHouse 可见时间的较晚者，包含客户端排队/重试。
- 统一每 50ms 加查询耗时轮询可见性，因此端到端数据是观测上界；观察查询也计入双方资源，不能把全部差异归因于 Kafka。结束后逐项核对 Owner/TraceId/SpanId。

## 相同故障：测量开始约 5 秒后停 ClickHouse，完全停止后保持 10 秒，再启动

故障负载每边 30 秒 / 30000 Span，仍使用相同字节输入和共同客户端策略：32 个在途 worker，最多 32 次退避重试、每批最多 90 秒；客户端进程始终存活，待发送数据保留在内存。

|路径|最终唯一 Span|停库期间到达的 Span|其中恢复前已确认|停库到达队列恢复 s¹|全轮端到端 P95 s|HTTP 尝试状态|
|---|---:|---:|---:|---:|---:|---|
|writer|30000/30000|10000|0|13.01|17.59|{'200': 300, '429': 102, '503': 305}|
|collector|30000/30000|10000|10000|20.48|27.38|{'200': 300}|

¹ 从启动 ClickHouse 的命令发起，到“停库期间到达的请求”全部确认且可查询；包含 ClickHouse 启动、退避、积压消化和观察查询。不是数据库 ready 后的纯处理时间。
两边最终均完整：旧版依赖仍存活客户端保留并重试未确认数据；新版可在 ClickHouse 停机时先确认 Kafka 持久接收，但这不等于已经落库。此次新版恢复更慢，不能宣称 Kafka 必然缩短恢复时间；当前 Consumer 指数退避最大 10 秒等配置会影响恢复尾部。

## 结论与边界

本机此负载下，新链路以更高 CPU、内存和端到端延迟，换取 ClickHouse 停机时仍可由 Kafka 承接并确认数据的能力。结果支持这是一个缓冲/可靠性取舍，不支持“加 Kafka 后更快”或企业级容量认证。
数据完整性条件必须同时说明：客户端存活并重试、Kafka 副本及磁盘正常、保留窗口未耗尽。本轮只注入 ClickHouse 进程停机，没有模拟客户端丢失、全机断电或跨故障域故障。
