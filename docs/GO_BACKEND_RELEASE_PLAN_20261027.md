# Catena Go 后端收尾计划

日期：2026-10-27。状态：任务队列和接入背压已实现并完成本地数据库验收；合成负载已测，部署发布门槛仍有未完成项。详见 [实现与验收记录](BACKEND_ENGINEERING_20261027.md)。

## 定位与范围

Catena：基于 Go 的 Agent Trace 数据接入与异步分析平台。
展示重点是可靠任务执行、数据写入与查询、身份隔离、可复现的故障和负载验收。
分析与 Harbor 实验提供真实业务负载；不宣称新的归因算法、RSI 效果或通用 Skill 收益。

保持 Go 单体控制面、PostgreSQL、ClickHouse、独立分析执行服务及 Harbor。
沿用已有部署方式。Redis、Kafka、Kubernetes、Service Mesh 和全面 gRPC 改造不进入本轮范围。
个人/团队记忆、更多角色、更多模型和新的前端模块暂停扩展。

## 改造前代码核对

| 能力 | 已确认的实现 | 本轮缺口 |
|---|---|---|
| 异步分析 | evolution_job.go 创建持久化 Job 后直接 `go s.executeEvolutionJob(...)` | 缺少持久领取、租约和进程崩溃接管 |
| 阶段状态 | 三阶段执行与单阶段 timeout，阶段结果写入数据库 | 数据库写入失败可能提前退出；未见后台恢复循环 |
| 创建幂等 | postgres.go 的 CreateEvolutionJob 使用唯一约束、指纹及冲突检查 | 创建幂等不等于执行/提交幂等 |
| 更新约束 | UpdateEvolutionJob 核对 owner 和来源等不变量 | 没有 lease/fencing 条件，无法挡住过期 Worker 写入 |
| OTLP 接入 | trace.go 有鉴权、16 MiB 请求限制、解码、租户身份绑定 | 需验证持续负载下的解码/写入并发、内存及过载反馈 |
| 写入 | ClickHouse InsertSpans 每请求 PrepareBatch/Append/Send，同步返回 | 是请求内批量，不是已实现跨请求异步批处理 |
| 查询 | 已有窄字段选 Trace ID、再取宽字段的优化和回归检查 | 需要固定版本、数据、缓存条件和并发下的重复测量 |
| CI | 已有 Go test/vet/race、Web、Python、Compose 检查定义 | 此次只读取配置，尚未确认远端当前构建结果；需加真实数据库故障门禁 |

## 工作包一：Reliable Job Execution

先覆盖现有 Evolution Job 路径，不同时重写全部任务系统。

### 实现范围

- PostgreSQL 存储领取与恢复所需的结构化调度字段：租约、worker、attempt、可运行时间、取消意图及单调递增 fencing token。
- 短事务内用 `FOR UPDATE SKIP LOCKED` 选择并领取任务；提交事务后才调用外部执行器。
- Go 有界 Worker Pool、可配置领取节奏、队列容量与优雅停止；API 创建后不再直接启动执行 goroutine。
- 心跳、阶段检查点和终态提交均校验当前租约、worker 与 fencing token。
- 租约过期可被新 Worker 领取；旧 Worker 恢复后不得续租或覆盖新结果。
- 暂时性故障采用有界退避与抖动；鉴权、参数和确定性输出错误不盲目重试。
- 恢复尽量从已提交阶段继续；结果提交和候选写入使用稳定业务键保证幂等。
- 取消为持久状态请求；Worker 确认后落终态。租约丢失时取消本地执行上下文。
- 指标覆盖队列深度、领取等待、执行耗时、重试、租约过期、取消和过期提交拒绝。

调度保证为 at-least-once；不承诺外部模型调用 exactly-once。
“模型已执行、结果未入库”窗口可能产生重复付费，必须在设计和故障报告中说明。
模型重复调用与结果重复落库分别计量。

### 必须通过的验收

1. 多 Worker 并发竞争时，单个有效租约只允许对应 Worker 提交结果。
2. 领取后、外部调用后、阶段提交前分别强杀进程；任务可在租约过期后恢复且不永久卡在 running。
3. 人为暂停旧 Worker、让新 Worker 接管，再恢复旧 Worker：旧 token 的心跳和结果均被拒绝。
4. 数据库短暂中断时有界等待/退避，不产生 goroutine 持续增长；恢复后队列继续运行。
5. 相同幂等键重复创建不增加 Job，相同结果重复提交不增加候选；不同请求指纹继续返回冲突。
6. 重试耗尽、取消、重启恢复和终态不回退均有集成测试；使用假执行器完成故障测试，不消耗模型额度。

## 工作包二：Trace Ingestion & Query Performance

### 实现范围

- 先记录现有路径基线，再按测得的瓶颈调整接入并发、单次 Span 数、内存预算、数据库连接池和查询范围。
- 控制在请求体读取/解码前实际生效；请求容量限制不能替代进程级有界并发。
- 过载明确返回可重试响应及重试提示；队列、goroutine 和内存不能无限增长。
- 第一版维持同步写入确认：ClickHouse Send 成功后才返回接收成功。
- 不以“放入进程内 channel”冒充持久接收成功。若后续确需提前确认，单独设计持久缓冲和恢复协议。
- 验证重复提交、Span 替换、尚未 merge 的读取、租户隔离、时间窗与稳定分页语义。
- 优化时保留字段/结果一致性检查；不通过删除 FINAL、忽略历史版本或缩小数据范围换取虚假加速。

### Benchmark 报告要求

分别报告固定真实语料和合成负载，记录硬件、资源上限、版本、数据哈希、宽字段大小分布、请求批大小与并发度。
固定预热、测量时长、重复次数；缓存条件不一致的结果不能直接当作优化比例。

记录接收/拒绝 Span/s、HTTP P50/P95/P99、错误率、过载率、RSS、goroutine、连接池等待、
ClickHouse 读取行/字节、查询耗时和落盘前后逻辑唯一计数。
数据库中断、并发突增和超大请求需独立测量。

不预先编造吞吐目标；基线后冻结性能目标。正确性门槛现在即可固定：
不能静默丢弃已确认的数据、不能跨租户读取、过载不能无限堆积，恢复后数据可读。
正式压测只在独立测试库或经授权的部署验收环境执行，不污染私人生产 Trace。
